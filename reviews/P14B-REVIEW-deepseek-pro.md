## Исходный текст ревью

Вердикт: правки до продолжения.

Дефекты:

1. **`--since HEAD~1` пропускает правки из более ранних коммитов при push нескольких коммитов**  
   `git diff --name-only HEAD~1` сравнивает последний коммит с его первым родителем. Если пуш содержит A → B → C, проверятся только изменения между B и C, изменения в A не анализируются. Правило «правка без отметки» обходится, если скилл правился в A без бампа, а в C скиллы не трогали.  
   → Использовать базовый коммит до всех новых коммитов: например, `git merge-base HEAD <базовая ветка>` или `${{ github.event.before }}` в CI, а не `HEAD~1`.

2. **Ошибки выполнения `git diff` и `git show` не обрабатываются**  
   `execFileSync` вызывается без `try/catch`. Если ref не существует (например, опечатка или shallow clone без нужной истории), процесс упадёт с неструктурированным исключением и стектрейсом вместо понятного сообщения.  
   → Обернуть вызовы в try/catch, выводить `[skills] ошибка git: <сообщение>` и завершать с кодом 2.

3. **Удаление скилла не контролируется**  
   Удалённые файлы отбрасываются через `!fs.existsSync(full)`. Удаление скилла — это тоже изменение каталога скиллов, но оно не требует отметки `version`/`updated`. Сейчас это не ошибка, но правило становится непоследовательным: добавить скилл можно без версии, удалить — молча.  
   → Либо явно разрешить удаление и задокументировать, либо добавить отдельную проверку (например, предупреждение) для удалённых скиллов.

4. **Ложное срабатывание при изменении только форматирования frontmatter без изменения значения `version`/`updated`**  
   `validateChangedSkill` сравнивает нормализованные значения из парсера. Если в файле изменились кавычки, пробелы или регистр ключей, но сами значения `version` и `updated` остались прежними, проверка выдаст ошибку «version и updated те же». Формально это соответствует требованию (изменение значения обязательно), но пользователь может ожидать, что любое текстовое изменение в поле считается «изменением». Это не дефект логики, но может вызывать недопонимание.  
   → Оставить как есть — правило строже и надёжнее.

Что из утверждений неверно:

- Утверждение «новый файл — не ошибка» верно, но реализация через `git show` даёт неожиданный эффект: если файл удалён и заново добавлен в одном коммите, `git show` возвращает старую версию, и файл будет проверен как изменённый, а не как новый. Это хорошо, но стоит учитывать.
- Утверждение «`--since HEAD~1` корректно» — неверно: оно работает только для одного нового коммита; при push нескольких коммитов часть изменений не проверяется.
