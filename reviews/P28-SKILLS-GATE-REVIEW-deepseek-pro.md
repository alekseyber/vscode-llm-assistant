## Что ревью нашло (важное)

**Мёртвый код `if (false)` в проверке «имя скилла = имя файла».** Причина не в правке, а в
прерванном прогоне мутаций: скрипт правит `src`, и если процесс убить между записью и
восстановлением, мутация остаётся в дереве. Так и вышло — гейт-проверка была отключена,
а `SKM-11` при этом проходил, потому что прогон мутаций шёл уже после тестов.

## Вердикт
**Правки до продолжения.** В текущем виде доработка содержит мёртвый код, ненадёжный парсинг frontmatter и неполное покрытие мутациями. Это может привести к ложным срабатываниям проверок и пропуску реальных ошибок в CI.

## Дефекты

### 1. Мёртвый код с `if (false)` — проверка `SKM-NO-NAME-PATH` фактически отключена
**Что не так:**  
В функции `validateSkillContent` есть строка:
```ts
if (false) {
    errors.push(`${filePath}: name «${name}» не совпадает с именем файла/каталога «${expected}»`);
}
```
Условие `if (false)` никогда не выполняется, поэтому проверка не работает. При этом в описании заявлена мутация `SKM-NO-NAME-PATH`, которая должна отключать именно эту проверку. Сейчас мутация ничего не меняет, а сама проверка отсутствует — гейт не проверяет соответствие имени и пути.

**Доказательство:**  
Строка `if (false)` в коде.

**Что делать:**  
Удалить мёртвый код и реализовать проверку с управлением через параметр, например:
```ts
if (shouldCheckNamePath) {
    if (name && expected && name.toLowerCase() !== expected) {
        errors.push(...)
    }
}
```
где `shouldCheckNamePath` зависит от мутации `SKM-NO-NAME-PATH`.

---

### 2. Ненадёжное отрезание frontmatter из-за BOM, пустых строк и внутренних `---`
**Что не так:**  
Регулярное выражение `^---\r?\n([\s\S]*?)\r?\n---` в `parseSkillFrontmatter` и `validateSkillContent` предполагает, что frontmatter начинается строго с первого символа файла и содержит ровно две строки `---` без лишних символов. Это не учитывает:
- BOM в начале файла (`\uFEFF`) — тогда `^---` не сработает.
- Пустые строки или пробелы перед `---` — тоже не сработает.
- Строку `---` внутри frontmatter (например, в значении многострочного поля, но многострочные значения уже запрещены проверкой на `|` или `>` — однако `---` может встретиться и без них, если это просто текст). Ленивое сопоставление `[\s\S]*?` остановится на первом `\r?\n---`, что может быть раньше настоящего конца frontmatter.

**Доказательство:**  
```ts
const raw = content.match(/^---\r?\n([\s\S]*?)\r?\n---/);
...
const body = content.replace(/^---\r?\n[\s\S]*?\r?\n---/, '').trim();
```
При наличии BOM `raw` будет `null`, а `body` останется всем содержимым файла, включая frontmatter.

**Что делать:**  
- Явно обрабатывать BOM: `content = content.replace(/^\uFEFF/, '')` перед всеми проверками.
- Либо потребовать, чтобы frontmatter начинался с первого символа без BOM, и добавить проверку на BOM как отдельную ошибку.
- Усовершенствовать регулярное выражение: разрешить необязательные пустые строки до и после, а также искать завершающий `---` как отдельную строку (например, с якорем `\n---\s*$` после содержимого). Для парсинга можно использовать библиотеку `js-yaml`, но тогда нужно определить поведение для плоского frontmatter.

### 3. Проверка пустого тела может не сработать из-за ошибок парсинга frontmatter
**Что не так:**  
Если frontmatter не распознан (например, из-за BOM или ведущих пробелов), `name` будет пустым, и условие `if (name && body.length === 0)` не выполнится. В результате пустой файл с формально корректным, но нераспознанным frontmatter не получит ошибку «пустое тело».

**Доказательство:**  
Та же строка, что в дефекте 2. Если `content` начинается с BOM, регулярка не сработает, `name` останется пустым, проверка тела пропустится.

**Что делать:**  
Исправить парсинг frontmatter (см. дефект 2), а затем убедиться, что `name` извлекается надёжно. При корректном парсинге эта проверка будет работать.

---

### 4. Недостаточное покрытие мутациями для полного тестирования гейта
**Что не так:**  
В доработке заявлены только три мутации: `SKM-NO-DUPLICATES`, `SKM-NO-SIZE`, `SKM-NO-NAME-PATH`. При этом в `validateSkillContent` есть и другие проверки:
- пустое тело скилла;
- формат `version` (`x.y.z`);
- формат `updated` (`YYYY-MM-DD`);
- запрет многострочного frontmatter (`|` или `>`);
- запрет вложенного YAML (строки с отступами);
- запрет пробелов в `name`.

Если какая-то из этих проверок не может быть отключена мутацией, невозможно написать тест, который проверяет, что гейт ловит именно эту проблему. Мотив из описания («гейт, который не проверен мутацией, может оказаться тестом, который не может упасть») применим ко всем проверкам.

**Доказательство:**  
В коде отсутствуют мутации для перечисленных проверок, а `if (false)` показывает, что даже заявленная `SKM-NO-NAME-PATH` не реализована. В тестах упомянуты только `SKM-16..17` (вероятно, покрывают новые мутации), но этого недостаточно.

**Что делать:**  
Добавить мутации для всех проверок в `validateSkillContent` (и, возможно, для других функций). Примеры имён: `SKM-NO-EMPTY-BODY`, `SKM-NO-VERSION-FORMAT`, `SKM-NO-UPDATED-FORMAT`, `SKM-NO-MULTILINE-FM`, `SKM-NO-NESTED-FM`, `SKM-NO-NAME-SPACES`. Это позволит создавать негативные тесты для каждой.

### 5. Рекурсия до трёх уровней — магическое число, возможны зацикливания на симлинках
**Что не так:**  
В описании указано, что CLI обходит `.claude/skills` рекурсивно до трёх уровней. Это жёстко заданное число без возможности настройки. Кроме того, если в дереве есть симлинки на родительские каталоги, рекурсия может зациклиться (даже при ограничении глубины, но она может не остановиться на симлинках, если проверка глубины выполняется до перехода, а симлинк ведёт наверх и глубина сбрасывается). В предоставленном фрагменте кода модуля нет рекурсивного обхода, но это замечание к общей доработке.

**Доказательство:**  
Описание пункта 2: «CLI `check-skills.js` обходит `.claude/skills` рекурсивно до трёх уровней». Отсутствует параметризация. Часто используют `fs.readdirSync(path, { withFileTypes: true })` и затем `dirent.isDirectory()`, но без проверки `dirent.isSymbolicLink()` можно попасть в цикл.

**Что делать:**  
- Вынести глубину в конфигурацию (переменная окружения, аргумент CLI, константа с пояснением).
- При обходе использовать `withFileTypes` и пропускать символические ссылки (`dirent.isSymbolicLink()`) или следовать им с отдельной защитой от циклов (Set посещённых реальных путей).

### 6. (Дополнительно) Проверка «правка помечена» в `validateChangedSkill` не учитывает случай, когда изменения не затрагивают содержимое инструкции
**Что не так:**  
Функция требует изменения `version` или `updated` при любом изменении файла. Однако если изменяются только незначащие части (например, форматирование Markdown, добавление пустых строк), это всё равно вызовет ошибку. Это может быть слишком строго, особенно для автоматических правок (например, Prettier). Стоит обсудить, нужно ли исключать whitespace-only изменения.

**Доказательство:**  
Код:
```ts
if (versionChanged || updatedChanged) return [];
return [`${filePath}: файл изменён, но version и updated те же — отметьте правку (version или updated)`];
```
Он сравнивает только `before` и `after` как строки, без учёта незначащих изменений.

**Что делать:**  
Если цель — ловить изменения смысла, можно сравнивать после нормализации (удаление пробелов, приведение к одному виду). Либо оставить как есть, но задокументировать, что любое изменение тела файла требует версии/даты. Это продуктовая дискуссия, но в рамках ревью стоит поднять вопрос.
