## Исходный текст ревью

1. **Вердикт:** правки до продолжения.

2. **Дефекты:**

   - **Парсер frontmatter не обрабатывает стандартный YAML и может давать ложные срабатывания/пропуски**  
     Доказательство: функция `parseSkillFrontmatter` разбирает только плоские строки вида `key: value`; многострочные блоки (`description: |`), вложенные структуры, комментарии, двоеточия в значениях без кавычек и одинарные/двойные кавычки с внутренними двоеточиями будут разобраны неверно или отброшены.  
     Что делать: либо использовать проверенную YAML-библиотеку (например, `yaml`), либо — если нужно остаться без зависимостей — явно ограничить поддерживаемый синтаксис и добавить проверку, что frontmatter не содержит многострочных/вложенных значений, иначе возвращать ошибку «unsupported YAML». Критичность для задачи средняя: задача — поймать немаркированную правку, но ложное срабатывание из-за легального YAML в реальном `SKILL.md` сделает гейт шумным.

   - **Нет проверки соответствия имени скилла имени файла/каталога**  
     Доказательство: `validateSkillContent` проверяет только наличие `name` и отсутствие пробелов, но не сверяет с `filePath`. Скилл с `name: foo` в файле `bar/SKILL.md` пройдёт гейт, но не будет найден рантаймом, если загрузчик ожидает структуру `<имя>/SKILL.md`.  
     Что делать: добавить проверку совпадения `name` с именем каталога (или именем файла для `.llma/skills/*.md`) — например, `path.basename(path.dirname(filePath)) === name`.

   - **Лимит размера продублирован в двух местах**  
     Доказательство: `MAX_SKILL_BYTES` в этом модуле и `MAX_SKILL_FILE_BYTES` в загрузчике — одна и та же константа; при изменении лимита в одном месте гейт и рантайм разойдутся.  
     Что делать: вынести общий лимит в отдельный модуль/константу и импортировать в оба места (или хотя бы добавить тест, который сравнивает экспортируемые значения после сборки).

   - **CLI обходит только первый уровень `.claude/skills/*/SKILL.md`**  
     Доказательство: `collect()` для директории заходит только на один уровень вложенности; если структура станет глубже (`skills/group/name/SKILL.md`), файлы не попадут в проверку, и скилл будет пропущен молча.  
     Что делать: либо явно заявить в справке и README, что поддерживается только один уровень (осознанное ограничение), либо реализовать рекурсивный обход до заданной глубины с тестом.

   - **Гейт не проверяет увеличение версии при изменении файла**  
     Доказательство: параметры задачи упоминают «поймать немаркированную правку», но текущая проверка статична; если кто-то правит `SKILL.md`, не меняя `version`/`updated`, гейт ничего не заметит.  
     Что делать: как минимум добавить в CI проверку, что при изменении `.md`-файла в PR соответственно изменена `updated` (или `version`). Это можно сделать отдельным шагом с diff, не обязательно в этом модуле.

   - **Нет проверки обязательных секций тела скилла**  
     Доказательство: проверяется только frontmatter, но не наличие/формат секций тела (например, `## Purpose`, `## Steps`), что оставляет возможной «пустую» инструкцию с корректным манифестом.  
     Что делать: если такие секции обязательны — добавить их проверку; если нет — явно указать в описании модуля, что тело не проверяется.

   - **«Скиллов нет → проверка проходит» делает гейт фиктивным для данного репозитория**  
     Доказательство: по фактам в репозитории расширения скиллов нет, CI всегда будет выводить «скиллов не найдено» и выходить с кодом 0, то есть гейт ничего не защищает.  
     Что делать: в таком репозитории либо убрать шаг, либо добавить хотя бы один тестовый/реальный скилл в репозиторий, чтобы гейт имел смысл; либо перенести проверку в репозиторий, где скиллы действительно есть.

3. **Что из моих утверждений неверно:**

   - Утверждение «необязательные поля, чтобы не заводить второй формат (совместимость с `SKILL.md`)» не соответствует реальности: стандартный `SKILL.md` может содержать полноценный YAML с вложенными структурами, а самописный парсер их не поддерживает — совместимость не достигается.
   - Утверждение «мутации 19/19» неверно интерпретировано: мутационное тестирование покрывает только модуль `SkillManifest.js`, но не интеграцию с CLI и не фактические ошибки парсинга на реальных YAML-конструкциях.
