### 2. Дефекты

#### **Дефект 1. Утечка внутренностей мока через `mockInternals()`**
- **Что не так:**  
  `mockInternals()` возвращает прямые ссылки на `workspace.__settings`, `workspace.__fs`, `workspace.__webviewPanels`, `languages.__inlineProviders` через объект `MockInternals`. Тесты могут произвольно мутировать эти структуры, минуя типизированные хелперы (`setSetting`, `setActiveEditor`, `lastWebviewPanel` и т.д.).
- **Доказательство:**  
  В харнессе:
  ```ts
  settings: workspace.__settings,
  fs: workspace.__fs,
  webviewPanels: workspace.__webviewPanels,
  inlineProviders: languages.__inlineProviders,
  ```
  Любой тест может сделать, например:
  ```ts
  mockInternals().settings['llmAssistant.autocomplete'] = { enabled: false };
  mockInternals().webviewPanels.length = 0; // или push фейковую панель
  ```
  Это обходит инкапсуляцию и создаёт несогласованное состояние, которое трудно отследить при рефакторинге. Нарушается принцип «единственное место с приведением типа и доступом к рычагам».
- **Что делать:**  
  Не возвращать прямые ссылки. Заменить на методы-мутаторы или readonly-прокси:
  ```ts
  settings(): Readonly<Record<string, unknown>>;
  addWebviewPanel(panel: WebviewPanelMock): void;
  clearWebviewPanels(): void;
  ```
  Если прямой доступ действительно нужен для некоторых тестов, явно пометить его как «escape hatch» и ограничить использование, например, через отдельную функцию `mockRawInternals()` с предупреждением в документации.

#### **Дефект 2. Цель «убрать `as any` и прямые обращения к внутренностям» не достигнута**
- **Что не так:**  
  По итогам осталось **292** `as any` и **101** обращение через приведение в 54 файлах. В `AGENTS.md` заявлено «в тестах без `as any`», но фактически значительная часть тестов всё ещё использует небезопасные приведения.
- **Доказательство:**  
  Пользователь сам приводит цифры: `as any` 318 → **292** (снижение ~8%), обращения через приведение 130 → **101** (~22%). Это не устранение, а лишь частичный перевод.
- **Что делать:**  
  Продолжить рефакторинг оставшихся тестов, переведя их на харнесс и фабрики. Для ускорения можно сгруппировать по категориям (например, работа с `window`, `workspace`, `languages`, `fetch`, создание доменных объектов) и применить шаблоны из уже готовых хелперов. Установить ESLint правило `@typescript-eslint/no-explicit-any: error`, чтобы CI блокировал новые случаи.

---

#### **Дефект 3. ESLint `warn` не предотвращает появление новых нарушений**
- **Что не так:**  
  Правило `@typescript-eslint/no-explicit-any` в `test/**` настроено как `warn`. CI падает только при `error`, поэтому предупреждения не блокируют мерж новых `as any`.
- **Доказательство:**  
  В описании: «ESLint: `@typescript-eslint/no-explicit-any: warn` для `test/**`». Если не настроен `--max-warnings 0` в CI, то число нарушений может снова расти.
- **Что делать:**  
  Установить `"@typescript-eslint/no-explicit-any": "error"` для `test/**` (или глобально), либо добавить в команду lint флаг `--max-warnings 0`. Это гарантирует, что новые `as any` не просочатся.

#### **Дефект 4. `fakeProvider` скрывает фиксированный размер чанка потока**
- **Что не так:**  
  `chat()` отдаёт ответ кусками по 16 символов. Это поведение неявно и может влиять на тесты, которые ожидают другой гранулярности (например, один чанк, чанки по строкам, или проверку порядка обработки).
- **Доказательство:**  
  ```ts
  for (let i = 0; i < text.length; i += 16) yield text.slice(i, i + 16);
  ```
  Если тест полагается на то, что весь ответ приходит одним куском, он либо неявно адаптирован под 16 символов, либо может сломаться при изменении размера. Сейчас это неочевидно из использования фабрики.
- **Что делать:**  
  Добавить опцию в `ProviderFakeOptions`, например, `chunkSize?: number` (по умолчанию 16) или `chunks?: string[]`, чтобы тесты могли контролировать разбиение. Это делает поведение прозрачным и предсказуемым.

#### **Дефект 5. Использование `as unknown as` в фабриках — обход цели по устранению небезопасных приведений**
- **Что не так:**  
  `fakeDocument`, `fakeTextEditor`, `fakeWebviewView` создают объекты с неполным набором полей и затем приводят их к типу через `as unknown as vscode.TextDocument` и т.д. Формально `as any` нет, но это тот же механизм обхода системы типов, просто менее заметный для статического анализа.
- **Доказательство:**  
  ```ts
  return { ... } as unknown as vscode.TextDocument;
  return { ... } as unknown as vscode.TextEditor;
  view = { ... } as unknown as vscode.WebviewView;
  ```
  Это позволяет пропустить обязательные поля интерфейса, и если тип изменится, тест не сломается на этапе компиляции, а может упасть в рантайме с неопределённым поведением. Заявленная цель «при добавлении обязательного поля тест перестанет компилироваться» не достигается для этих фабрик.
- **Что делать:**  
  Рассмотреть альтернативы:
  - Использовать `satisfies` и явно перечислить все обязательные поля, заполнив их фейковыми значениями.
  - Применить вспомогательные утилиты типа `createStub<T>()` с проверкой полноты через mapped types.
  - Если полное соответствие невозможно из-за огромного количества полей VS Code, явно задокументировать это как осознанное исключение и добавить `// eslint-disable-next-line @typescript-eslint/no-explicit-any` с пояснением, но тогда честно признать, что часть обвязки остаётся небезопасной.

### 3. Что из утверждений автора неверно
1. **«В тестах без `as any`»** — неверно: осталось 292 `as any` в 54 файлах.
2. **«Единственное место с приведением типа»** — не соответствует действительности: в харнессе есть несколько `as unknown as` (`workspace`, `windowMock`, `languages`), а в фабриках `fakeDocument`, `fakeTextEditor`, `fakeWebviewView` также используют `as unknown as`.
3. **«Переведены на харнесс/фабрики: ...»** — утверждение неполное: перечисленные модули переведены, но большинство остальных (54 файла) не затронуты, поэтому общая цель этапа не выполнена.
4. **«ESLint `warn` достаточно для контроля»** — неверно: `warn` не блокирует CI, если не задан `--max-warnings 0`.
5. **«Замер: `as any` 318 → 292 ...» как главный результат** — снижение незначительное и не свидетельствует о завершении рефакторинга; критерий успеха должен быть «0 `as any` и 0 обращений через приведение», а не уменьшение на 8–22%.
