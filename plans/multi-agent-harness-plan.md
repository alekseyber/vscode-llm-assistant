## Концепция: Multi-Agent Harness

**Идея:** плагин становится «упряжью» (harness) для оркестрации нескольких AI-агентов, работающих параллельно в одном workspace.

### Архитектура

```
┌─────────────────────────────────────────────┐
│              Orchestrator Agent              │
│  (системный промпт: «разбей задачу, распредели│
│   между воркерами, собери результаты»)        │
└──────────┬──────────┬──────────┬────────────┘
           │          │          │
     ┌─────▼────┐ ┌───▼───┐ ┌───▼──────┐
     │ Worker 1 │ │Worker 2│ │ Worker 3 │
     │ (coder)  │ │(tests) │ │(review)  │
     └──────────┘ └────────┘ └──────────┘
           │          │          │
           └──────────┼──────────┘
                      ▼
              Shared Workspace
              (файлы, git, артефакты)
```

### Ключевые сущности

```typescript
interface AgentRole {
  name: string;           // «coder», «reviewer», «architect»
  systemPrompt: string;   // специализированный промпт
  allowedTools: string[]; // ограничение инструментов
  model?: string;         // своя модель (слабая/дешёвая для простых задач)
}

interface MultiAgentTask {
  id: string;
  goal: string;           // общая цель
  roles: AgentRole[];     // роли для воркеров
  strategy: 'parallel' | 'sequential' | 'pipeline';
}
```

### Режимы работы

**1. Parallel (параллельный)**
- Оркестратор разбивает задачу на независимые подзадачи
- Каждый воркер получает свою часть, работает одновременно
- Результаты объединяются оркестратором

**2. Sequential (последовательный)**
- Цепочка: Архитектор → Кодер → Тестировщик → Ревьюер
- Каждый получает результат предыдущего
- Подходит для строгих пайплайнов

**3. Pipeline (конвейер)**
- Как sequential, но каждый агент работает над своим файлом/артефактом
- Например: генерация кода → генерация тестов → запуск тестов → фикс

### Фаза A: Базовая multi-agent инфраструктура (MVP)

#### Задача MA-1: AgentWorker

Новый модуль `src/modes/apply/AgentWorker.ts`:
- Изолированный `messages[]` массив
- Свой `systemPrompt` из `AgentRole`
- Свой `allowedTools` (allow-list на уровне воркера)
- Возможность указать отдельного провайдера/модель
- Обёртка над `runAgentLoop`

| AC | Критерий |
|----|----------|
| MA-1.1 | `AgentWorker` принимает `AgentRole` и создаёт изолированный контекст |
| MA-1.2 | Воркер использует свой `systemPrompt`, не затрагивая глобальный |
| MA-1.3 | `allowedTools` на уровне воркера ограничивает доступные инструменты |
| MA-1.4 | Можно указать отдельную модель для воркера (не глобальную) |
| MA-1.5 | `AgentWorker.run(task)` возвращает `{answer, steps, tokens}` |
| MA-1.6 | `npm run compile` без ошибок |
| MA-1.7 | `npm run test:mocked` — все существующие тесты проходят |
| MA-1.8 | Новые юнит-тесты для `AgentWorker` (мок-провайдер) |

#### Задача MA-2: AgentOrchestrator

Новый модуль `src/modes/apply/AgentOrchestrator.ts`:
- Принимает задачу и массив ролей
- Создаёт воркеров (AgentWorker)
- Запускает параллельно (Promise.all) или последовательно
- Собирает результаты в сводный отчёт

| AC | Критерий |
|----|----------|
| MA-2.1 | `AgentOrchestrator` принимает `MultiAgentTask` и создаёт N воркеров |
| MA-2.2 | Режим `parallel` — все воркеры запускаются одновременно |
| MA-2.3 | Режим `sequential` — каждый следующий получает результат предыдущего |
| MA-2.4 | Результаты всех воркеров собираются в `MultiAgentResult` |
| MA-2.5 | Ошибка одного воркера не роняет весь оркестратор |
| MA-2.6 | `npm run compile` без ошибок |
| MA-2.7 | `npm run test:mocked` — все тесты проходят |
| MA-2.8 | Юнит-тесты для оркестратора (мок-воркеры) |

## Пример использования

**Задача:** «Реализуй REST API для списка задач»

**Оркестратор разбивает:**
1. **Архитектор** (модель: DS V4 Pro, инструменты: read_file, write_file)  
   → Проектирует структуру: `DESIGN.md`
2. **Кодер** (модель: DS V4 Flash, инструменты: write_file, run_terminal)  
   → Пишет `server.ts` по DESIGN.md
3. **Тестировщик** (модель: Qwen Coder, инструменты: write_file, run_terminal)  
   → Пишет `server.test.ts`, запускает тесты
4. **Ревьюер** (модель: DS V4 Pro, инструменты: read_file, patch_file)  
   → Проверяет код, вносит правки

**Результат:** 4 агента работают параллельно/последовательно, пользователь видит прогресс в UI.
