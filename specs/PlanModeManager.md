## Назначение

Режим планирования для Agent Mode: вместо прямого ReAct-цикла задача сначала анализируется и создаётся детальный план реализации, затем план утверждается пользователем и выполняется через оркестратор с последующей рефлексией.

Активируется переключателем «📋 Plan» над textarea (только для agent-режима, по умолчанию выключен).

## Этапы

```
Пользователь → [📋 Plan ON] → задача
  │
  ├─ Этап 1: ПЛАНИРОВАНИЕ
  │     PlannerAgent (изолированный):
  │       • Анализирует задачу
  │       • Изучает затронутые файлы (read_file/search_files)
  │       • Создаёт план по структуре → .llma/plans/<uuid>-<slug>.md
  │     UI: показывает план + «✅ Имплементировать» / «✏️ Исправить»
  │
  ├─ Этап 2: ИМПЛЕМЕНТАЦИЯ (по кнопке «✅»)
  │     Оркестратор (architect → coder):
  │       • Чистый контекст
  │       • Задача: «Реализуй план из .llma/plans/<uuid>.md»
  │       • Coder отмечает выполненные AC в плане (⬜ → ✅)
  │
  └─ Этап 3: РЕФЛЕКСИЯ
        ReviewerAgent:
          • Читает план → проверяет все AC
          • Докладывает: ✅ выполнено / ❌ не выполнено (с деталями)
          • Coder исправляет замечания → Reviewer перепроверяет
          • Максимум 2 цикла рефлексии
```

## Интерфейс

### `PlanModeManager`

```typescript
class PlanModeManager {
  /** Сгенерировать план (Этап 1) */
  async generatePlan(task: string, provider: any, model: string, workspacePath: string): Promise<PlanResult>

  /** Запустить имплементацию (Этап 2) */
  async implementPlan(planPath: string, provider: any, model: string): Promise<ImplementResult>

  /** Запустить рефлексию (Этап 3) */
  async reflect(planPath: string, provider: any, model: string): Promise<ReflectResult>
}
```

### `PlannerAgent` — агент-планировщик

Изолированный агент (AgentWorker) со специализированным промтом. Только читает код, не пишет.

### `ReviewerAgent` — агент-рефлексии

AgentWorker с промтом ревьюера. Сравнивает результат с планом, проверяет AC, докладывает.

### Структура плана (файл `.llma/plans/<uuid>-<slug>.md`)

```markdown
# План: <краткое название>
**ID:** plan-<uuid>
**Цель:** <одно предложение>
**Дата:** <ISO timestamp>
**Контекст:** <исходный запрос>

## 📦 Затронутые компоненты
| Компонент | Файл | Тип изменения |

## 🔧 Этапы реализации
### Этап N: <название>
- [ ] Что сделать
- [ ] Файлы
- [ ] Зависимости

## ✅ Контрольные точки (AC)
| ID | Критерий | Способ проверки | Статус |

## 🔍 Инструкция для ревьюера
### Что проверять
### Критерии ОТКЛОНЕНИЯ
### Формат отчёта

## ⚠️ Риски
| Риск | Вероятность | Митигация |

## 📝 История
| Дата | Событие |
```

## Контракты

| Ситуация | Поведение |
|----------|-----------|
| Plan Mode ON + agent-режим | Ветвление в handleSendMessage: запуск PlannerAgent |
| Plan Mode OFF + agent-режим | Обычный ReAct (текущее поведение) |
| Plan Mode ON + chat-режим | Игнорируется — обычный чат |
| План создан, пользователь нажал «✏️ Исправить» | Возврат в чат, пользователь уточняет задачу |
| План создан, пользователь нажал «✅ Имплементировать» | Этап 2 → оркестратор |
| Оркестратор завершил | Этап 3 → рефлексия |
| Рефлексия: reviewer нашёл проблемы | Coder исправляет → reviewer перепроверяет (макс. 2 цикла) |
| Рефлексия: reviewer подтвердил | Финальный отчёт пользователю |
| `.llma/plans/` не существует | Создаётся автоматически |
| Ошибка на любом этапе | Сообщение пользователю, план сохраняется (можно перезапустить) |

## Промпты

### PlannerAgent (системный)

```
Ты — архитектор-планировщик. Твоя задача — создать детальный план реализации.

1. Проанализируй запрос пользователя
2. Изучи затронутые файлы через инструменты (read_file, search_files, list_files)
3. Создай план по СТРОГОЙ структуре ниже
4. Запиши план через write_file в .llma/plans/<uuid>-<slug>.md

Ты НЕ пишешь код. Только план.

Структура плана:
- # План: <краткое название>
- ID, Цель, Дата, Контекст
- 📦 Затронутые компоненты (таблица)
- 🔧 Этапы реализации (конкретные действия, файлы, зависимости)
- ✅ Контрольные точки (критерии успеха + способ проверки)
- 🔍 Инструкция для ревьюера (что проверять, критерии отклонения, формат отчёта)
- ⚠️ Риски (что может пойти не так, митигация)

Важно: каждый пункт AC должен иметь КОНКРЕТНЫЙ способ проверки (не «проверить что работает», а «запустить npm test, убедиться что тест X проходит»).
```

### ReviewerAgent (системный)

```
Ты — ревьюер. Твоя задача — проверить реализацию по плану.

1. Прочитай план из .llma/plans/<id>.md
2. Проверь КАЖДЫЙ пункт AC из таблицы «Контрольные точки»
3. Для каждого AC — используй указанный способ проверки
4. Составь отчёт в формате:

✅ AC-1: <что проверил, результат>
❌ AC-2: <что не так, конкретная команда/файл/скриншот>

НЕ ИСПРАВЛЯЙ код. Только докладывай.
Если все AC ✅ — напиши «ПЛАН ВЫПОЛНЕН ПОЛНОСТЬЮ».
```

## Связи

- **Использует:** AgentWorker (PlannerAgent, ReviewerAgent), AgentOrchestrator (имплементация), ChatViewProvider (ветвление), WebView UI (переключатель + кнопки)
- **Файлы планов:** `<workspace>/.llma/plans/plan-<uuid>-<slug>.md`
- **Модели:** PlannerAgent — глубокое мышление (deepseek-v4-pro), ReviewerAgent — быстрое (deepseek-v4-flash)
