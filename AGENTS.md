# AGENTS.md — правила для AI-агентов в этом проекте

## ⚠️ ПРЕЖДЕ ВСЕГО: спецификации

**В `specs/` лежат 38 спецификаций компонентов** (+3 мета: ARCHITECTURE, TRACEABILITY, TEMPLATE) — интерфейсы, контракты, детали реализации, тесты.
⚠️ НЕ загружай все сразу. Алгоритм:

**Для изменения существующего кода:**
1. Прочитай `specs/ARCHITECTURE.md` — карта проекта
2. Найди нужный компонент → прочитай ТОЛЬКО его spec
3. Изменил `src/X.ts` → в том же коммите обнови `specs/X.md`: бамп `version` + строка в «Истории изменений»

**Для новой фичи:**
1. Прочитай `specs/ARCHITECTURE.md` — полная карта, потоки данных, компоненты
2. Прочитай `specs/TRACEABILITY.md` — связи spec → AC → тест → код
3. Определи затронутые компоненты — прочитай ИХ spec (обычно 2-4 шт.)
4. Создай новый spec по `specs/TEMPLATE.md`
5. `📋` — представь план пользователю на утверждение

Шаблон: [`specs/TEMPLATE.md`](specs/TEMPLATE.md)
Карта проекта: [`specs/ARCHITECTURE.md`](specs/ARCHITECTURE.md)
Валидатор: `node scripts/spec-validate.js`

## Язык и стиль
- Комментарии в коде — на русском языке
- Имена переменных/классов/функций — на английском
- Ответы пользователю — на русском, кратко, по делу

## Формат ответа
- Markdown для форматирования
- Без воды и длинных вступлений
- Код в блоках ``` с указанием языка

## Инструменты

- write_file — запись файлов
- patch — точечные замены
- search_files — поиск
- terminal — выполнение команд

## Подводные камни

- **Git pathspec `specs/**/*.md`** не матчит файлы в корне `specs/` (требует минимум один уровень вложенности).
  Используй `grep '^specs/.*\.md$'` или добавь `'specs/*.md'` вторым pathspec.
- **`\b` в JS-регексах не работает с кириллицей.** Используй `(?:^|\s)` и `(?:\s|[?!.]|$)` вместо `\b`.
- **`[object Object]` в WebView:** если модель — объект `{name, pricing}`, извлекай `.name` при рендеринге select.

## Процесс разработки (SDD)

1. **Архитектурное обсуждение** → фиксация решений
2. **Spec** → `specs/<Component>.md`: интерфейс, контракты, AC, связи
3. **План** → `PLAN.md`: задачи с AC, гейты между этапами
4. **Код** → реализация по spec
5. **Тесты** → проверка AC (команды `npm test`)
6. **Приёмка** → `npm run compile && npm run lint && npm test`

### Трассировка

```
spec → AC → тест → код
  ↓
PLAN.md (задачи привязаны к AC)
```

### Структура spec-файла

```markdown
---
component: ИмяКомпонента
version: X.Y.Z
status: stable | beta | deprecated | planned
---

## Назначение
## Интерфейс
## Контракты (таблица: ситуация → поведение)
## AC (таблица: ID → критерий → статус)
## Связи (использует / используется)
## История изменений
```

### Целостность спек (обязательные правила)

1. **`version` = последняя запись «Истории изменений».** Изменил компонент → бамп `version` + строка в истории **в том же коммите**. Проверяет `spec-validate.js` (4 проверки) и CI `sdd-check` — нарушение = красный CI.
2. **Спека без кода (spec-first)** → `status: planned` (не требует src-файла, освобождена от обратной проверки).
3. **Удаление компонента** → `status: deprecated` или удалить файл спеки.
4. **`ARCHITECTURE.md`** обновлять при: добавлении/удалении/переименовании компонента, изменении карты компонентов или покрытия.
5. **Не-.ts компоненты** (WebView — фронтенд JS/HTML/CSS) — спека без src-файла, это норма (в `REVERSE_EXEMPT_SPECS` валидатора).
