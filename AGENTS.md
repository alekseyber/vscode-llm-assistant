# AGENTS.md — правила для AI-агентов в этом проекте

## ⚠️ ПРЕЖДЕ ВСЕГО: спецификации

**В `specs/` лежат 38 спецификаций компонентов** (+3 мета: ARCHITECTURE, TRACEABILITY, TEMPLATE) — интерфейсы, контракты, детали реализации, тесты.
⚠️ НЕ загружай все сразу. Алгоритм:

**Для изменения существующего кода:**
1. Прочитай `specs/ARCHITECTURE.md` — карта проекта
2. Найди нужный компонент → прочитай ТОЛЬКО его spec
3. Изменил `src/X.ts` → в том же коммите обнови `specs/X.md`: бамп `version` + строка в «Истории изменений». Это проверяет локальный pre-commit хук (`bash scripts/install-git-hooks.sh`): CI-гейт смотрит один коммит, и бамп «следующим коммитом» оставляет исходный красным навсегда

**Для новой фичи:**
1. Прочитай `specs/ARCHITECTURE.md` — полная карта, потоки данных, компоненты
2. Прочитай `specs/TRACEABILITY.md` — связи spec → AC → тест → код
3. Определи затронутые компоненты — прочитай ИХ spec (обычно 2-4 шт.)
4. Создай новый spec по `specs/TEMPLATE.md`
5. `📋` — представь план пользователю на утверждение

Шаблон: [`specs/TEMPLATE.md`](specs/TEMPLATE.md)
Карта проекта: [`specs/ARCHITECTURE.md`](specs/ARCHITECTURE.md)
Валидатор: `node scripts/spec-validate.js`

## Подводные камни

- **Git pathspec `specs/**/*.md`** не матчит файлы в корне `specs/` (требует минимум один уровень вложенности).
  Используй `grep '^specs/.*\.md$'` или добавь `'specs/*.md'` вторым pathspec.
- **`\b` в JS-регексах не работает с кириллицей.** Используй `(?:^|\s)` и `(?:\s|[?!.]|$)` вместо `\b`.
- **`[object Object]` в WebView:** если модель — объект `{name, pricing}`, извлекай `.name` при рендеринге select.

## Процесс разработки (SDD)

1. **Архитектурное обсуждение** → фиксация решений
2. **Spec** → `specs/<Component>.md`: интерфейс, контракты, AC, связи
3. **План** → `PLAN.md`: задачи с AC, гейты между этапами
4. **Код** → реализация по spec
5. **Тесты** → проверка AC (команды `npm test`)
6. **Приёмка** → `npm run compile && npm run lint && npm test`

**Гейт «код → спека» (один носитель).** Правило живёт в `scripts/sdd-check.sh`: изменённый `src/**/Component.ts`
требует `specs/Component.md` с **поднятым `version`** (не просто «файл тронут»). Локально ставится хуком —
`cp scripts/sdd-check.sh .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit` (хуки в git не коммитятся,
поэтому установка — обязанность при клонировании). В CI тот же файл вызывается как `--range HEAD~1..HEAD`;
инлайн-дубль удалён, чтобы локальная проверка не могла быть слабее CI. Обход только осознанно: `--no-verify`.

### Релизный график: поезд, а не ручеёк

- **Публикация — раз в неделю, поездом** (воскресенье вечером). Всё смерженное в `main` копится, версия в `package.json` между релизами не меняется.
- **Минимальный интервал между публикациями — 48 часов.** Даже если есть что выпустить: за это время всплывают жалобы на предыдущую версию.
- **Хотфикс вне очереди** — только два повода: расширение не активируется или закрывается дыра в безопасности. Не «мелкая правка, которая не терпит».
- **Версии:** плановый поезд — minor (`0.24.0`), хотфикс — patch (`0.24.1`). По номеру видно, что было в релизе.
- **Гейт на теге (механика):** весь Test — `spec-validate`, `lint` (внутри CHANGELOG и спеки), `check-any-budget`, `test-unit`, `test-e2e` — плюс VSIX-смоук и сверка имени тега с `version` в `package.json`. **Evals идут отдельным прогоном на теге и публикацию не блокируют:** недоступный судья — не свойство релиза, гейт на нём встаёт ни на чём. Публикация — только после подтверждения.

Причина правила измерена: за вечер 12.11 вышло шесть версий (0.23.4–0.23.9), и по истории невозможно понять, какая из них сломала панель истории. Шесть публикаций — это шесть прогонов гейтов и шесть записей, которые никто не читает.

### Защита веток и тегов (rulesets, 15.11.2026)

- **`main`** — активный ruleset `id 27310355`: запрещены force-push, удаление ветки и merge-коммиты (история линейная). Прямой push разрешён: работа соло идёт мелкими коммитами, PR на каждый шаг — налог без выгоды.
- **`refs/tags/v*`** — активный ruleset `id 27310356`: запрещены удаление и перезапись тега. Тег — это то, что уходит в Marketplace; переставить его на другой коммит нельзя.
- **Required status checks в ruleset не включаются.** Замерено живым пушем 15.11: ruleset с обязательными checks отклоняет сам пуш — `required_status_checks | fail | 5 of 5 required status checks are expected` (у нового коммита прогонов ещё нет). Классическая branch protection так себя не ведёт — она гейтит только merge. Для ruleset «required checks» означает «только через PR», а PR на каждый шаг в соло-режиме отклонён.
- **`sdd-check` не годится в обязательные и в PR-режиме**: он запускается с фильтром путей (`src/**/*.ts`, `specs/**/*.md`) и на PR без этих правок висел бы в pending всегда.
- **Защита от красного релиза — job `tests` в `publish.yml`**: тег публикуется только тогда, когда весь Test на этом коммите зелёный. Evals идут отдельным прогоном на теге и публикацию не блокируют.

Runbook.
- *Секрет в истории:* переписать `main` при живом ruleset нельзя → ротировать секрет (стирания из истории в публичном репо недостаточно) → снять ruleset → переписать историю → создать ruleset заново.
- *Ошибка в теге:* bypass-листа у правил на тегах нет (в личном репо он недоступен) → `PATCH` ruleset в `enforcement: disabled`, переставить тег, вернуть `active`.
- *Понадобился гейт на отдельный коммит без PR:* пуш в ветку → дождаться зелёного Test на этом SHA → fast-forward в `main`. В ruleset это не проверено: обязательные checks в правилах сейчас выключены.

### Два правила границ (взяты из разбора DeepSeek Harness)

- **Plugins, not loop changes.** Новое поведение добавляется на документированных точках расширения (тулы, скиллы, режимы, провайдеры). Изменение агентского цикла — не «ещё одна фича», а правка архитектуры: сначала `ARCHITECTURE.md` и спека, потом код. Причина: цикл — единственное место, где ошибка ломает всё сразу, а расширение ломает только свою ветку.
- **Explicit > implicit на границах.** Значение по умолчанию — явный шаг разрешения (`resolve(request): Spec` в том, кто владеет решением), а не скрытый `?? default` внутри `run()`. Причина: скрытый дефолт нельзя ни увидеть в конфиге, ни проверить тестом, ни объяснить в предупреждении — он всплывает только как «почему оно так себя ведёт».

### Структура spec-файла

```markdown
---
component: ИмяКомпонента
version: X.Y.Z
status: stable | beta | deprecated | planned
---

## Назначение
## Интерфейс
## Контракты (таблица: ситуация → поведение)
## AC (таблица: ID → критерий → статус)
## Связи (использует / используется)
## История изменений
```

### Целостность спек (обязательные правила)

1. **`version` = последняя запись «Истории изменений».** Изменил компонент → бамп `version` + строка в истории **в том же коммите**. Проверяет `spec-validate.js` (4 проверки) и CI `sdd-check` — нарушение = красный CI.
2. **Спека без кода (spec-first)** → `status: planned` (не требует src-файла, освобождена от обратной проверки).
3. **Удаление компонента** → `status: deprecated` или удалить файл спеки.
4. **`ARCHITECTURE.md`** обновлять при: добавлении/удалении/переименовании компонента, изменении карты компонентов или покрытия.
5. **Не-.ts компоненты** (WebView — фронтенд JS/HTML/CSS) — спека без src-файла, это норма (в `REVERSE_EXEMPT_SPECS` валидатора).
- **Мутационная проверка:** правим одну строку в src — тесты обязаны упасть. `npm run check:mutation` (19 мутаций). Неприменимая мутация (не компилируется) считается «неприменимой», а не пойманной.

- **Тесты и типы:** новые тесты пишем без `as any`; в существующих приведений 292 — снижаем при правке файла, отдельной задачей не гонимся. Нужна возможность мока — функция из `test/support/vscode-harness.ts`; нужен двойник доменного типа — фабрика из `test/support/fakes.ts`. Бюджет — `npm run check:test-any`: пофайловый ратчет, рост только с причиной, `as unknown as` считается отдельно (9 шт.).
